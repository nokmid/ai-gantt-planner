# Roadmap to production

Документ фиксирует, что в текущей реализации сделано осознанно упрощённо
ради скорости тестового задания, какие риски это создаёт и в каком порядке
это стоит закрывать перед реальным продакшн-использованием.

## 1. Технические долги, оставленные сознательно

### 1.1 Хранилище данных — in-memory + JSON-дамп на диск
**Сейчас:** `TaskStore` держит задачи в памяти процесса, дублируя в JSON-файл
рядом с кодом. Один процесс = один общий план для всех пользователей.

**Риск:** при рестарте контейнера на бесплатных тарифах хостинга (Render free
tier усыпляет процесс) файловая система может быть эфемерной — план потеряется.
Нет multi-tenancy: два разных пользователя видят и правят один и тот же план.
Нет конкурентного доступа — гонка при одновременной правке из двух вкладок.

**Порядок закрытия:** заменить на PostgreSQL (SQLAlchemy/SQLModel), добавить
`project_id`/`user_id` в модель Task, привязать план к проекту, а не быть
глобальным синглтоном. Это первое, что нужно сделать перед реальными
пользователями — приоритет **высокий**.
> **Наблюдалось на практике при тестировании:** импорт второго тестового
> Excel-файла (сценарий "мобильное приложение") в одной вкладке браузера
> перезаписал общий план на сервере, пока в другой вкладке оставался открыт
> первый сценарий (тестовые данные из seed). Диаграмма в старой вкладке
> продолжала показывать прежние задачи (React-состояние не обновляется
> само по себе), но чат-агент при следующем запросе обращался уже к
> актуальному серверному состоянию — и корректно не нашёл задачу "Backend
> API" (она была заменена импортом), вместо этого предложил похожую
> "Настройка бэкенда" и переспросил, прежде чем что-либо менять. То есть
> сам защитный механизм (п. 1.7, переспрашивать при неоднозначности)
> сработал правильно — а вот рассинхронизация диаграммы с реальным
> состоянием сервера — это и есть прямое проявление данного технического
> долга. Лечится тем же способом (п. 1.1) — привязкой плана к
> пользователю/сессии вместо глобального хранилища на весь сервер.

### 1.2 Каскадный пересчёт дат при переносе задачи не реализован
**Сейчас:** `move_task`/`shift_task` двигают только саму задачу. Если у неё
есть зависимые задачи, их даты не пересчитываются — план может стать
визуально противоречивым (стрелка зависимости "из будущего в прошлое").

**Риск:** для реального PM-инструмента это критично — план должен оставаться
непротиворечивым после любой правки, иначе ему нельзя доверять.

**Порядок закрытия:** реализовать топологический пересчёт: при переносе
задачи A найти все задачи, зависящие от A (прямо и транзитивно), и сдвинуть
их начало не раньше нового `end_date` предшественника. Нужно решить продуктовый
вопрос: сдвигать автоматически всегда, или спрашивать подтверждение
("это затронет 4 задачи, применить?") — второе безопаснее для доверия
пользователя. Приоритет **высокий**, это ядро ценности продукта.

### 1.3 Нет валидации циклических зависимостей
**Сейчас:** `add_dependency` не проверяет, не создаёт ли новая зависимость
цикл (A зависит от B, B зависит от A).

**Риск:** циклическая зависимость сломает любые расчёты дат и, вероятно,
зациклит будущий каскадный пересчёт из пункта 1.2.

**Порядок закрытия:** перед добавлением зависимости — обход графа (DFS) на
предмет цикла, отклонять с понятной ошибкой, которую агент сможет
объяснить пользователю в чате. Приоритет **высокий**, должно делаться
вместе с 1.2.

### 1.4 История чата — одна глобальная переменная в памяти процесса
**Сейчас:** `_history` в `routers/chat.py` — общий для всех запросов к серверу.

**Риск:** при нескольких одновременных пользователях их диалоги смешаются.
При рестарте контейнера история теряется.

**Порядок закрытия:** привязать историю к session_id (cookie/JWT) и хранить
в Redis или той же Postgres. Приоритет **средний** — для демо одного
пользователя не критично, но блокирует любой multi-user сценарий.

### 1.5 In-process MCP вместо отдельного MCP-сервера
**Сейчас:** MCP-инструменты вызываются как обычные python-функции внутри
того же процесса FastAPI, а не через отдельный MCP-сервер по stdio/SSE.

**Почему так:** для одного контейнера с одним клиентом это меньше движущихся
частей и меньше точек отказа при деплое тестового задания.

**Риск:** если в будущем понадобится переиспользовать эти же инструменты
из другого клиента (например, Slack-бота или CLI) — придётся выносить.

**Порядок закрытия:** это не долг, а сознательная архитектурная граница.
Схема инструментов уже отделена от способа их вызова (`_build_openai_tools`
в `llm_agent.py`), так что вынос в отдельный MCP-сервер — это изолированное
изменение одного файла, не переписывание бизнес-логики. Приоритет **низкий**,
делать только если появится второй клиент инструментов.

### 1.6 Нет аутентификации и авторизации
**Сейчас:** любой, у кого есть URL, может смотреть и менять план.

**Риск:** для продакшена неприемлемо в принципе.

**Порядок закрытия:** добавить auth (например, Clerk/Auth0 или простой
JWT + email), привязать проекты к пользователям, добавить роли
(viewer/editor) — вероятно нужно для реального B2B-использования, где не
все участники должны иметь право переносить чужие задачи. Приоритет
**высокий** перед любым реальным использованием за пределами демо.

### 1.7 Резолюция задачи по имени в чате — только точное совпадение и подстрока
**Сейчас:** `_resolve_task` сначала ищет id, потом точное совпадение имени
(без учёта регистра), потом первое частичное совпадение по подстроке.

**Риск:** при похожих названиях задач ("Тестирование" и "Интеграционное
тестирование") частичный матч может задеть не ту задачу, и агент молча
применит изменение не к тому, что имел в виду пользователь.

**Порядок закрытия:** при неоднозначности (>1 совпадение) инструмент должен
возвращать список кандидатов, а системный промпт — явно требовать от модели
переспросить пользователя вместо угадывания. Приоритет **средний**.

### 1.8 Excel-импорт заменяет весь план целиком
**Сейчас:** `POST /api/excel/import` вызывает `store.replace_all()` —
загрузка нового файла полностью стирает текущий план, без слияния.

**Риск:** случайная потеря правок, сделанных через чат, если пользователь
повторно загрузит старый файл.

**Порядок закрытия:** либо явное предупреждение в UI ("это заменит текущий
план"), либо режим слияния по названию задачи. Приоритет **средний**.

## 2. Чего не хватает для продакшена (за пределами перечисленных долгов)

- **Тесты.** Сейчас проверялась только синтаксическая корректность
  (`py_compile`) в среде без интернета — нет unit-тестов на резолюцию
  зависимостей, парсинг Excel, agent loop с моками LLM-ответов.
- **Наблюдаемость.** Нет логирования вызовов LLM, стоимости токенов,
  метрик латентности агентного цикла — без этого невозможно контролировать
  расходы на OpenRouter в проде.
- **Rate limiting / защита от злоупотреблений** на `/api/chat` — сейчас
  ничто не мешает засыпать эндпоинт запросами и исчерпать бюджет на LLM.
- **Undo/history плана.** Один неверно понятый агентом запрос ("удали
  задачу X") сейчас необратим кроме как руками через модалку/новый импорт.
  Для доверия пользователя нужен минимум soft-delete или version history.
- **Локализация дат/форматов** — сейчас всё жёстко на русском и в формате
  ISO-дат, для международного использования потребуется i18n.

## 3. Риски

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Агент неверно интерпретирует неоднозначный запрос и меняет не ту задачу | Средняя | Высокое (потеря доверия) | Переспрашивать при неоднозначности (1.7), лог действий в чате уже виден пользователю |
| Циклическая зависимость ломает расчёт дат | Средняя (после реализации 1.2) | Высокое | Валидация циклов (1.3) |
| Рост стоимости LLM при частом использовании чата | Высокая при масштабировании | Среднее | Rate limiting, выбор более дешёвой модели через `OPENROUTER_MODEL`, кэширование list_tasks |
| Потеря данных при перезапуске контейнера | Высокая на бесплатных тарифах | Высокое | Переход на управляемую БД (1.1) — первый приоритет |

## 4. Рекомендуемый порядок закрытия

1. БД вместо in-memory (1.1) — без этого всё остальное бессмысленно масштабировать
2. Каскадный пересчёт дат + валидация циклов (1.2 + 1.3) — ядро продуктовой ценности
3. Аутентификация и привязка проектов к пользователям (1.6)
4. Сессионная история чата в БД (1.4)
5. Тесты + наблюдаемость
6. Остальное — по мере появления реальных пользователей и обратной связи
