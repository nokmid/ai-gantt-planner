# Промт: AI Gantt Planner

Скопируйте весь текст ниже целиком в чат с AI-ассистентом (Claude, GPT,
Cursor, Windsurf и т.п.) — этого достаточно, чтобы получить рабочий проект.
Промт написан от первого лица разработчика, ставящего задачу.

---

## Роль и контекст

Ты — full-stack разработчик. Нужно построить AI-native веб-приложение:
интерактивная диаграмма Ганта с редактированием плана через чат на
естественном языке. Ниже — полное техническое задание, включая
обязательный стек, формат данных и критерии, по которым решение будут
оценивать (акцент на логику и корректную обработку условий, а не на
объём кода).

## Продуктовый сценарий

1. Пользователь открывает страницу и сразу видит диаграмму Ганта с
   тестовыми (засидированными) данными.
2. Может загрузить свой Excel со списком задач вместо тестовых —
   диаграмма перестраивается.
3. Рядом с диаграммой — чат. Пользователь пишет на естественном языке,
   что изменить в плане: перенести задачи, поменять зависимости,
   добавить новые задачи, перераспределить исполнителей. Изменения от
   агента мгновенно отражаются на диаграмме.
4. Клик по задаче открывает модалку с деталями задачи (состав деталей —
   на усмотрение разработчика).
5. План можно экспортировать обратно в Excel.

## Обязательный стек

- Фронтенд: React
- Бэкенд: Python / FastAPI
- MCP (Model Context Protocol) — инструменты для изменения плана должны
  быть оформлены как MCP tools, а не как прямые вызовы функций из LLM-кода
- LLM через API — конкретный провайдер: **OpenRouter**
  (https://openrouter.ai/api/v1, OpenAI-совместимый интерфейс,
  выбор модели — переменная окружения, чтобы можно было переключать
  Claude/GPT/Gemini без изменения кода)

## Формат входного Excel

Колонки ровно такие: `задача | описание | исполнитель | длительность | предшественники`.

Важно: предшественники в файле указаны **названиями задач через запятую**,
а не id — это удобно для человека, заполняющего файл руками. Импорт должен
сам резолвить имена в id и **каскадно восстанавливать даты**: если у задачи
есть предшественник, её старт = дата окончания предшественника (+1 день);
если предшественников несколько — берётся самая поздняя дата окончания
среди них; если предшественников нет — старт = сегодня. Реализуй это как
рекурсивный обход графа зависимостей (топологически), а не как обработку
строк по порядку сверху вниз — файл может ссылаться на задачу, которая
описана ниже по списку.

## Архитектура: как именно должен работать чат с ИИ (это ядро задания)

Не давай LLM редактировать данные напрямую текстом. Схема обязательна такая:

1. Все возможные изменения плана оформи как конечный набор **MCP-инструментов**
   с чёткой JSON-схемой аргументов: перенос задачи на дату, сдвиг на N дней,
   изменение длительности, смена исполнителя, добавление/удаление зависимости,
   добавление новой задачи, удаление задачи, изменение процента готовности,
   получение списка всех задач.
2. При запросе пользователя в чате: отдай LLM список этих инструментов через
   tool calling (function calling), LLM решает, какой инструмент вызвать и с
   какими аргументами — но не выполняет изменение сама.
3. Твой backend-код реально выполняет соответствующую детерминированную
   функцию, меняющую состояние плана.
4. Результат выполнения (успех или ошибка) верни обратно модели как
   tool result, чтобы она могла либо вызвать следующий инструмент (если
   запрос составной, например "перенеси задачу и переназначь исполнителя"),
   либо сформулировать финальный текстовый ответ пользователю.
5. Заверни это в цикл с ограничением числа итераций (защита от
   зацикливания, например максимум 8 шагов).

Инструмент поиска задачи по названию должен уметь резолвить и точное
совпадение (без учёта регистра), и частичное — но при **нескольких**
совпадениях должен возвращать список кандидатов, а не угадывать первый
попавшийся: пусть модель переспросит пользователя, какую именно задачу он
имел в виду. Это важно — не позволяй агенту молча применять изменение не
к той задаче.

Системный промпт агента должен явно требовать:
- вызывать инструменты, а не только описывать изменения текстом;
- при неоднозначности или ненайденной задаче — переспрашивать, а не выдумывать;
- при составных запросах, затрагивающих несколько задач — сначала получить
  актуальный список задач через соответствующий инструмент, потом применять
  изменения по каждой подходящей задаче отдельно;
- формат дат — строго YYYY-MM-DD;
- после выполнения — кратко (1–3 предложения) сказать, что именно изменено.

## Требования к данным

Задача содержит: id, название, описание, исполнителя, дату начала,
длительность в днях, список предшественников **по id** (не по имени —
имена только во входном/выходном Excel и в интерфейсе чата), процент
готовности. Дата окончания вычисляется из даты начала и длительности,
не хранится отдельно, чтобы не могла рассинхронизироваться при переносе.

## UX/UI — не ограничивайся минимальным набором, вот на что обратить внимание

- Диаграмма должна визуально показывать зависимости между задачами
  (стрелки от одной задачи к другой), сегодняшнюю дату отдельной линией,
  выходные дни, прогресс выполнения задачи заливкой внутри бара, разных
  исполнителей — разным цветом.
- В чате должна быть видна "прозрачность" действий агента: какие именно
  инструменты были вызваны с какими аргументами по каждому ответу (можно
  сворачиваемым блоком, чтобы не загромождать диалог).
- При изменении плана через чат — визуально подсвети на диаграмме именно
  те задачи, которые были затронуты, на пару секунд, чтобы пользователь
  видел, что именно поменялось, не сравнивая план вручную до/после.
- Модалка деталей задачи должна показывать не только поля для правки, но
  и список задач, от которых текущая зависит, и список задач, которые
  зависят от неё — в обе стороны.
- Предусмотри пустое состояние (нет задач), состояние загрузки, и понятные
  сообщения об ошибках (например, при некорректном Excel — какая именно
  колонка отсутствует, а не общий "ошибка 400").
- Дизайн — не используй дефолтные шаблонные стили конструктора; выбери
  осознанную цветовую и шрифтовую систему, разграничь визуально рабочую
  область диаграммы и панель чата.

## Осознанно НЕ делай (но зафиксируй как технический долг, не скрывай)

- Каскадный автоматический пересчёт дат зависимых задач при переносе
  предшественника — не реализуй в MVP, но задокументируй как известное
  ограничение с объяснением, почему (нужно решать продуктовый вопрос:
  сдвигать всегда автоматически или спрашивать подтверждение).
- Валидацию циклических зависимостей — тоже вынеси в технический долг,
  не в реализацию, если не хватает времени, но обязательно опиши риск.
- Многопользовательский доступ, аутентификацию, персистентную БД — можно
  in-memory хранилище с дампом в JSON-файл для одного демо-процесса,
  но явно опиши в документации, что это неприемлемо для реального
  продакшена и что нужно заменить на управляемую БД с привязкой к
  пользователю/проекту.

## Критерий успеха

Решение будут оценивать в первую очередь по логике и корректной обработке
условий (в том числе граничных: неоднозначные запросы в чате, отсутствующие
задачи, некорректный Excel, составные запросы, затрагивающие несколько
задач), а не по объёму или изяществу кода. Задание одинаковое для всех
кандидатов — выделиться нужно продуктовым мышлением и вниманием к деталям,
а не просто фактом, что задание выполнено технически.
