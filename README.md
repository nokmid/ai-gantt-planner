# AI Gantt Planner

Веб-приложение: интерактивная диаграмма Ганта с загрузкой/выгрузкой Excel и
редактированием плана через чат на естественном языке (ИИ-агент с MCP-инструментами).

Тестовое задание: full-stack разработчик AI-native продукта (React + FastAPI).

## Демо

- Ссылка на приложение: **https://ai-gantt-planner-delta.vercel.app**
- Бэкенд (API): **https://ai-gantt-planner-1.onrender.com** — проверка здоровья: `/api/health`
- Демо-видео/gif: `demo.gif` в корне репозитория
- Пример Excel для теста: [`examples/example_tasks.xlsx`](examples/example_tasks.xlsx)

> **Важно про первую загрузку:** бэкенд задеплоен на бесплатном тарифе Render,
> который "усыпляет" сервис примерно через 15 минут без запросов. Если
> диаграмма долго не загружается при первом открытии — это нормально,
> сервер "просыпается" 30–50 секунд, дальше работает быстро. Для реального
> продакшена нужен платный тариф без усыпления (см. `docs/roadmap-to-production.md`).

## Архитектура

```
┌─────────────┐        REST/JSON        ┌──────────────────┐
│   React     │ ───────────────────────▶│     FastAPI       │
│  (Vite SPA) │◀─────────────────────── │                   │
└─────────────┘                          │  ┌─────────────┐ │      ┌────────────┐
                                          │  │  MCP tools   │◀┼─────▶│ OpenRouter │
                                          │  │ (9 функций)  │ │      │ (LLM API)  │
                                          │  └─────────────┘ │      └────────────┘
                                          │  ┌─────────────┐ │
                                          │  │ TaskStore    │ │
                                          │  │ (in-memory + │ │
                                          │  │  JSON dump)  │ │
                                          │  └─────────────┘ │
                                          └──────────────────┘
```

**Ключевая идея:** между "языком человека в чате" и "реальным изменением
плана" стоит строгий контракт из 9 MCP-инструментов (`backend/app/mcp/tools.py`) —
`move_task`, `shift_task`, `reassign_task`, `add_dependency`, `remove_dependency`,
`add_task`, `delete_task`, `set_progress`, `list_tasks`. LLM не редактирует
данные напрямую — она только **решает, какую функцию вызвать с какими
аргументами**; само изменение делает обычный детерминированный Python-код.
Это и защита от галлюцинаций, и то, что превращает произвольный текстовый
запрос в контролируемое действие.

Схема инструментов зарегистрирована один раз в простом реестре `TOOLS`
(`backend/app/mcp/tools.py`) — имя, описание, JSON Schema аргументов рядом
с каждой функцией — и переиспользуется как источник схемы для tool calling
через OpenRouter (`backend/app/llm_agent.py`). Изначально это было сделано
через библиотеку `mcp`/FastMCP, но она требует Python ≥3.10, а часть машин
(в т.ч. системный `/usr/bin/python3` на Mac) идёт с 3.9 — поэтому та же идея
реализована вручную без внешней зависимости, без изменения сути подхода.

### Слои бэкенда

| Файл | Отвечает за |
|---|---|
| `app/models.py` | Модель `Task`, in-memory хранилище + persist в JSON, seed-данные |
| `app/mcp/tools.py` | 9 MCP-инструментов — единственный способ менять план |
| `app/llm_agent.py` | Агентный цикл: даём модели инструменты, исполняем то, что она просит вызвать |
| `app/excel_service.py` | Импорт (имя→id предшественников, каскадный расчёт дат) и экспорт |
| `app/routers/*.py` | REST API поверх всего вышеперечисленного |

### Компоненты фронтенда

| Файл | Отвечает за |
|---|---|
| `GanttChart.jsx` | Кастомная SVG-диаграмма: бары, зависимости-стрелки, сегодня, выходные |
| `ChatPanel.jsx` | Чат с агентом, лог вызванных инструментов (прозрачность действий ИИ) |
| `TaskModal.jsx` | Детали задачи по клику: правка полей, список зависимостей в обе стороны |
| `ExcelControls.jsx` | Импорт/экспорт |

## Формат входного Excel

Колонки: `задача | описание | исполнитель | длительность | предшественники`.
Предшественники указываются **названиями** задач через запятую (не id) —
бэкенд сам резолвит имена и восстанавливает даты каскадно от самого раннего
предшественника. Пример — `examples/example_tasks.xlsx`.

## Локальный запуск

### Бэкенд
```bash
cd backend
python -m venv venv && source venv/bin/activate  # Windows: venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env   # вписать свой OPENROUTER_API_KEY
uvicorn app.main:app --reload --port 8000
```

### Фронтенд
```bash
cd frontend
npm install
npm run dev
```
Откройте http://localhost:5173 — Vite сам проксирует `/api` на `localhost:8000`
(см. `vite.config.js`).

## Деплой

Задеплоено именно так:

**Бэкенд (Render):**
1. Web Service → Language: Docker → Root Directory: `backend`
2. Environment Variables: `OPENROUTER_API_KEY`, `OPENROUTER_MODEL=anthropic/claude-sonnet-4.6`, `CORS_ORIGINS=*`
3. Free tier — единственный нюанс: сервис засыпает без трафика, первый запрос после простоя может занять 30–50 секунд

**Фронтенд (Vercel):**
1. Import Project → Framework Preset: Vite (определяется автоматически) → Root Directory: `frontend`
2. Environment Variables: `VITE_API_BASE_URL=https://ai-gantt-planner-1.onrender.com`

## Как использовались ИИ-ассистенты при разработке

Проект написан с помощью Claude (Anthropic) в режиме агентной разработки:
модель проектировала архитектуру (разделение MCP tools / agent loop / REST
layer), генерировала код бэкенда и фронтенда файл за файлом, писала CSS и
компоновку интерфейса, и формировала эту документацию. Ключевые решения —
выбор модели данных (id-ссылки вместо текстовых), решение не делать
каскадный пересчёт дат в MVP, выбор кастомного SVG вместо готовой Gantt-
библиотеки — принимались осознанно в диалоге, с объяснением trade-off'ов
(см. `docs/roadmap-to-production.md`), а не приняты вслепую от модели.
Код проверялся на синтаксическую корректность (`python -m py_compile`)
в среде без доступа в интернет — установка зависимостей и полноценный
рантайм-тест сделаны локально после сборки.

## UX/UI решения сверх базового ТЗ

Задание прямо разрешало не ограничиваться описанным минимумом — вот что
добавлено сверх него:

- **Стрелки зависимостей между задачами** на диаграмме — в ТЗ требовалось
  только показывать диаграмму, визуализация связей между задачами не
  оговаривалась
- **Прогресс выполнения задачи** — заливка внутри бара по проценту
  готовности; поля `progress` вообще не было в требуемом формате Excel,
  добавлено как отдельная сущность модели
- **Цветовое кодирование по исполнителю** — детерминированный цвет на
  основе имени, чтобы визуально группировать нагрузку по людям без
  дополнительного клика
- **Линия "сегодня" и подсветка выходных дней** на сетке диаграммы
- **Подсветка задач, изменённых агентом** — после каждого ответа в чате
  затронутые бары на диаграмме на пару секунд подсвечиваются, чтобы не
  нужно было сравнивать план до/после вручную
- **Прозрачность действий агента** — сворачиваемый лог под каждым ответом
  чата с точными именами вызванных инструментов и аргументами
- **Подсказки-примеры запросов** в чате при первом открытии — снижают
  порог входа для человека, не понимающего, что вообще можно спросить
- **Взаимные зависимости в модалке задачи** — не только список
  предшественников, но и список задач, которые зависят от текущей
- **Осознанная дизайн-система** — рабочая область диаграммы и панель чата
  визуально разграничены (светлая/тёмная), а не стандартные шаблонные
  стили конструктора, чтобы подчеркнуть разницу между "просмотр плана" и
  "командный режим" общения с ИИ
- **Понятные сообщения об ошибках при импорте Excel** — называется
  конкретно отсутствующая колонка, а не общий код ошибки

Известное ограничение UI, оставленное осознанно, — отсутствие адаптивности
под мобильные экраны, задокументировано в `docs/roadmap-to-production.md`
(пункт 1.9) вместе с объяснением trade-off.
