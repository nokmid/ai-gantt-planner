# AI Gantt Planner

Веб-приложение: интерактивная диаграмма Ганта с загрузкой/выгрузкой Excel и
редактированием плана через чат на естественном языке (ИИ-агент с MCP-инструментами).

## Архитектура

```
┌─────────────┐        REST/JSON        ┌──────────────────┐
│   React     │ ───────────────────────▶│     FastAPI       │
│  (Vite SPA) │◀─────────────────────── │                   │
└─────────────┘                          │  ┌─────────────┐ │      ┌────────────┐
                                          │  │  MCP tools   │◀┼─────▶│ OpenRouter │
                                          │  │ (9 функций)  │ │      │ (LLM API)  │
                                          │  └─────────────┘ │      └────────────┘
                                          │  ┌─────────────┐ │
                                          │  │ TaskStore    │ │
                                          │  │ (in-memory + │ │
                                          │  │  JSON dump)  │ │
                                          │  └─────────────┘ │
                                          └──────────────────┘
```

**Ключевая идея:** между "языком человека в чате" и "реальным изменением
плана" стоит строгий контракт из 9 MCP-инструментов (`backend/app/mcp/tools.py`) —
`move_task`, `shift_task`, `reassign_task`, `add_dependency`, `remove_dependency`,
`add_task`, `delete_task`, `set_progress`, `list_tasks`. LLM не редактирует
данные напрямую — она только **решает, какую функцию вызвать с какими
аргументами**; само изменение делает обычный детерминированный Python-код.
Это и защита от галлюцинаций, и то, что превращает произвольный текстовый
запрос в контролируемое действие.

Схема инструментов зарегистрирована один раз через `FastMCP` и переиспользуется
и как MCP-сервер (для совместимости со стандартом), и как источник схемы
для tool calling через OpenRouter (`backend/app/llm_agent.py`).

### Слои бэкенда

| Файл | Отвечает за |
|---|---|
| `app/models.py` | Модель `Task`, in-memory хранилище + persist в JSON, seed-данные |
| `app/mcp/tools.py` | 9 MCP-инструментов — единственный способ менять план |
| `app/llm_agent.py` | Агентный цикл: даём модели инструменты, исполняем то, что она просит вызвать |
| `app/excel_service.py` | Импорт (имя→id предшественников, каскадный расчёт дат) и экспорт |
| `app/routers/*.py` | REST API поверх всего вышеперечисленного |

### Компоненты фронтенда

| Файл | Отвечает за |
|---|---|
| `GanttChart.jsx` | Кастомная SVG-диаграмма: бары, зависимости-стрелки, сегодня, выходные |
| `ChatPanel.jsx` | Чат с агентом, лог вызванных инструментов (прозрачность действий ИИ) |
| `TaskModal.jsx` | Детали задачи по клику: правка полей, список зависимостей в обе стороны |
| `ExcelControls.jsx` | Импорт/экспорт |

## Формат входного Excel

Колонки: `задача | описание | исполнитель | длительность | предшественники`.
Предшественники указываются **названиями** задач через запятую (не id) —
бэкенд сам резолвит имена и восстанавливает даты каскадно от самого раннего
предшественника. Пример — `examples/example_tasks.xlsx`.

## Локальный запуск

### Бэкенд
```bash
cd backend
python -m venv venv && source venv/bin/activate  # Windows: venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env   # вписать свой OPENROUTER_API_KEY
uvicorn app.main:app --reload --port 8000
```

### Фронтенд
```bash
cd frontend
npm install
npm run dev
```
Откройте http://localhost:5173 — Vite сам проксирует `/api` на `localhost:8000`
(см. `vite.config.js`).

## Деплой

**Бэкенд (Render / Fly.io / любая VM):**
1. Задеплоить `backend/` как Docker-сервис (Dockerfile уже есть) либо как обычный
   Python-сервис с командой `uvicorn app.main:app --host 0.0.0.0 --port $PORT`
2. Указать переменные окружения: `OPENROUTER_API_KEY`, `OPENROUTER_MODEL`,
   `CORS_ORIGINS=https://<домен фронтенда>`

**Фронтенд (Vercel):**
1. Импортировать `frontend/` как проект, framework preset — Vite
2. Переменная окружения `VITE_API_BASE_URL=https://<домен бэкенда>`

## Как использовались ИИ-ассистенты при разработке

Проект написан с помощью Claude (Anthropic) в режиме агентной разработки:
модель проектировала архитектуру (разделение MCP tools / agent loop / REST
layer), генерировала код бэкенда и фронтенда файл за файлом, писала CSS и
компоновку интерфейса, и формировала эту документацию. Ключевые решения —
выбор модели данных (id-ссылки вместо текстовых), решение не делать
каскадный пересчёт дат в MVP, выбор кастомного SVG вместо готовой Gantt-
библиотеки — принимались осознанно в диалоге, с объяснением trade-off'ов
(см. `docs/roadmap-to-production.md`), а не приняты вслепую от модели.
Код проверялся на синтаксическую корректность (`python -m py_compile`)
в среде без доступа в интернет — установка зависимостей и полноценный
рантайм-тест сделаны локально после сборки.
